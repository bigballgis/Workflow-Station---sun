# AI 护栏 — 你最容易犯的错

以下是 LLM 在本项目中最常见的失败模式。每次写代码时自我检查。

## 幻觉防御

### 幽灵 API（最高频）
你经常"发明"不存在的方法/类/字段。**引用任何符号前必须 Grep 确认它存在。**
- 引用一个类 → 搜索确认它在哪个包
- 调用一个方法 → 搜索确认签名（参数类型、返回类型）
- 使用一个字段 → 搜索确认它叫什么、什么类型
- 导入一个包 → 确认 pom.xml / package.json 中有这个依赖

### 幽灵依赖
不要引入项目中不存在的依赖。如果确实需要新依赖，**必须明确告知用户**并说明原因。

## 风格漂移防御

### 模式复制而非发明
新代码必须**复制同模块已有文件的精确模式**，不要发明"更好"的写法：
- 发现同模块用 `LinkedHashMap` → 你也用，不要换成 `HashMap`
- 发现同模块异常用 `ErrorContext.builder()` → 你也用，不要用 `new ErrorContext()`
- 发现同模块测试用 `@BeforeEach` 初始化 → 你也用，不要用构造器

### 过度工程化
- 不要添加"以防将来需要"的抽象层
- 不要把简单的 if-else 重构为策略模式
- 不要在只有一个实现的地方强行抽接口（除非分层架构要求）

## 上下文丢失防御

### 长对话漂移
对话越长，你越容易忘记早期上下文。当对话超过 10 轮时：
- 重新阅读关键文件，不要凭记忆
- 重新搜索确认之前提到的类名/方法名
- 如果用户纠正了你，承认错误并立即修正

### 部分修改综合征
修改一个文件时容易遗忘其关联文件。始终问自己：
- 改了接口 → 实现类？
- 改了后端 DTO → 前端类型？
- 改了 Entity → SQL 脚本？MapStruct Mapper？
- 改了 i18n key → 三个 locale 文件？

## 绝对禁止

- 生成你无法解释其作用的代码
- 用 `// TODO` 标记代替实际实现（除非用户明确要求占位）
- 在不理解现有代码的情况下重写它
- 假设"编译通过 = 逻辑正确"
