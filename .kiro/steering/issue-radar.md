# 问题雷达 — 始终开启

你在执行任何任务时（包括不相关任务），阅读到的每一个文件都是一次审查机会。
发现范围外的问题时，**立即记录到 `.kiro/issues/index.yaml`**，不要等，不要忘。

## 扫描触发条件

| 类别 | 标签 | 识别信号 |
|------|------|---------|
| Bug | 🔴/🟡 | 逻辑错误、返回值错误、条件判断反转、空指针风险 |
| 安全 | 🔴 | 硬编码密钥、SQL 拼接、未校验输入、越权风险 |
| 性能 | 🟢 | N+1 查询、循环内创建对象、未用索引、不必要的深度 watch |
| 技术债 | 🟢 | `@SuppressWarnings`、过宽的 catch、硬编码魔法值、重复代码 |
| 缺失测试 | 🟡 | 核心业务逻辑无测试覆盖、边界条件未测试 |
| 前后端不同步 | 🟡 | DTO 字段名不一致、API 端点前端调用但后端不存在 |

## 跟踪系统结构

```
.kiro/issues/
├── index.yaml    ← 所有 issue 索引（唯一数据源）
└── README.md     ← 格式说明
.kiro/issues.md   ← 仪表盘摘要（统计 + 待处理清单）
```

## 记录新问题

在 `.kiro/issues/index.yaml` 末尾追加一条 YAML 条目：

```yaml
- id: "{下一个编号，三位数字}"
  status: open
  severity: critical/major/minor
  category: security/bug/performance/architecture/quality/deploy
  summary: "一句话描述问题"
```

## 记录前检查

1. 搜索 `index.yaml` 确认问题未重复（`grep "关键词" .kiro/issues/index.yaml`）
2. 确认编号递增（当前最大编号 +1）

## 修复后更新

在 `index.yaml` 中将对应条目的 `status` 改为 `fixed`，添加 `fixed_at` 字段：
```yaml
  status: fixed
  fixed_at: "2026-03-31"
```

同时更新 `.kiro/issues.md` 仪表盘中的统计和待处理清单。

## 你绝不应该做的

- 发现问题后"记在心里"但不写入文件 — 下次对话你会忘记
- 在不相关任务中"顺便修复"范围外的问题 — 记录它，让用户决定何时处理
- 降低问题优先级来避免记录 — 宁可记录后被用户标记为不需要处理
