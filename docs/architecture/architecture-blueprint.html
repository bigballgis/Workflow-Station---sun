Q1

每个系统负责什么？

一句话原则：设计时（DW）产出蓝图 → 运行时（WE）执行流程 → 门户（UP）承载终端用户 → 治理（AC）管账号与平台。四个业务后端职责互不重叠，共享层只提供能力、不含业务。

developer-workstation DW

设计时 · 建模

可视化设计 Function Unit：表 / 字段 / FK-PK / 关联表 / 表单 / 视图访问 / BPMN / 决策 / 动作 / 邮件规则；版本管理与导入导出、克隆。

不做 不承载终端用户运行时；不消费门户消息；生产环境非常驻。

workflow-engine-core WE

运行时 · 流程引擎

部署 BPMN、启动 / 流转流程实例、任务分派、多实例、流程完成回调、邮件入站（IMAP）同步。底层 Flowable 7。

待办处理、发起流程、填写表单、我的申请、关联表（MI）子表数据、站内信 / 通知、权限自助申请。

共享层  platform-security（JWT/鉴权/身份主数据）· platform-cache（Redis）· platform-messaging（Kafka 事件+通知）· platform-common（DTO/异常/工具，ApiResponse<T>）—— 只提供能力，绝不反向依赖任何业务后端。

Q4

哪些方向禁止依赖？

七条红线守住模块边界。评审新增依赖 / 调用 / 建表时逐条对照。

F1

platform-* 禁止依赖任何业务后端

共享层是叶子 / 地基，反向即成环。 后果：Maven 循环依赖、全量重编、无法独立发版。

F2

业务后端之间禁止编译期 JAR 依赖（AC/UP/DW/WE 互不 import）

保持服务可独立构建 / 发版；跨服务只走 HTTP / 事件。 后果：退化为「分布式单体」，改一处全体重编。

F3

任何服务禁止直接读写 Flowable act_* 表

引擎数据仅 WE 独占，只经 HTTP 访问。 后果：绕过引擎一致性、破坏流程状态。

F4

任何服务禁止写非自己前缀的表（如 UP 写 dw_*、AC 写 up_*）

单一写方保证数据主权；跨前缀只读且需登记。 后果：数据归属混乱、并发覆盖、审计断链。

F5

生产运行链路禁止依赖 developer-workstation

DW 是设计时系统，SIT/UAT/PROD 默认不部署。 后果：生产因缺 DW 故障 —— 故 UP 取表单必须有共享库回退。

F6

前端禁止直连 Kong Admin API / 跳过 Kong 直连后端（生产）

网关治理由后端治理域编排；边缘统一 JWT。 后果：绕过鉴权与限流。

F7

platform-common 禁止继续膨胀（现 110+ 类 god module）

爆炸半径最大，改一 DTO 触发 4 服务重编。 见优化方案 P1-1 拆分计划。

依赖方向总则

共享层被业务层依赖，业务层之间只经 HTTP / 事件；数据按前缀单一写方、跨前缀只读且登记；引擎数据只经 HTTP；设计时系统不进生产运行链路。
