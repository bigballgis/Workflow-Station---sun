## 运行中发现并修复的三处遗漏

1. 首步自动提交：原路径重复领取已经分配给发起人的任务，触发 `ASSIGNMENT_STATE_CHANGED`；随后仍准备走旧完成接口。新增 `AssignmentInitialTaskCompletion`，受保护首步使用稳定操作 UUID 和完成账本，以 `SUBMIT` 保留操作语义，接受后不再调用旧完成及快照路径。初始历史仍记录，业务投影由账本同步独占，Pending／Conflict 不误报为尚未完成，响应包含操作 ID 和同步状态。公共完成入口拒绝伪造 `SUBMIT`；Engine 锁内再次核验真实原发起人、持有人、顶层轮次、冻结发起人任务及无已完成任务。重复领取回归先失败后通过：`tmp/assignment-first-start-red.log`、`tmp/assignment-first-start-green.log`。
2. 假持有人：原 `TaskInfoAssembler` 在实际 holder 已清空时，仍根据发起人配置补上 liam，导致备用人页面显示 Held。补全现在只对明确识别的 legacy 任务生效。保护任务按真实 holder 和候选返回。参数测试保护分支先红、修后保护和 legacy 都绿：`tmp/assignment-holder-red.log`、`tmp/assignment-holder-green.log`；同一真实待办 Held → Claim，李娜显式领取后 SQL 确认 holder 为 `user-e2e-lina`、来源 BACKUP。
3. 查询缓存误提交：受保护且未启用 batch runtime 的表单会回传只读 Lookup 缓存 `rt:sys_users`，后端正确返回 403。前端根据服务端 `assignmentClaimAccess.tracked` 扩展已有可写 store 投影；发送仅包含声明可写绑定，保存后保留页面只读缓存。未按表名过滤，legacy 分支保持原行为。反例使用改名目录缓存，先红后绿，并实际保存验证缓存保留：`tmp/assignment-lookup-cache-red.log`、`tmp/assignment-lookup-cache-green.log`。同任务新前端已消除自动保存错误并完成办理。

审查处置：启动路径遗漏及 SQL 错误被忽略两项已关闭；通用 SUBMIT 会绕过审批动作的 Major 已关闭；保存后会清掉本地只读缓存的问题已关闭。后端和前端增量分别经过独立重审，已验证范围 PASS，无未处置的 Major。结论不覆盖全仓无关测试或所有 FU／角色组合。
