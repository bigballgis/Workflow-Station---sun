一句话：只有数据 flow 能连数据库。Service Task 和普通 flow 自己都不连库，要查数据、改数据，就去调用数据 flow。

「调用数据 flow」是什么

它是给普通 flow 用的一个组件（英文名 Call Data Flow），只做一件事：选一个数据 flow，把参数传过去，再把结果拿回来。它本身不连数据库，所以任何 workspace 的普通 flow 都能用。

为什么要专门做它？普通 flow 现在要调用另一个 flow，只能用 http 组件去打对方的 webhook 地址，问题有三个：

走一遍例子：采购流程计算折扣

  1. 1流程走到 Service Task，它调用普通 flow「采购-计算折扣」。
  2. 2普通 flow 用「调用数据 flow」组件调用「查询供应商」，拿到供应商信息。
  3. 3普通 flow 用 FU 专属组件「计算折扣」算出折扣 8%。这一步只算，不碰数据库。
  4. 4普通 flow 调用数据 flow「更新订单折扣」，把 8% 写回订单。
  5. 5结果返回给 Service Task，流程继续往下走。

调外部系统：HTTP 组件 + Admin Center 连接

外部系统不单独做组件，也不单独成一类。Admin Center 新增「连接」管理：每个连接按环境存外部系统的地址、用户名、密码。flow 里的 HTTP 组件选一个连接，只填接口路径，就能调外部 API。

在哪做什么
Admin Center建连接：名称（各环境相同）、地址、认证方式、用户名、密码。uat、prod 各填各的值。
DW 的 flowHTTP 组件选连接，填路径（例如 /orders）、方法、请求体。flow 里没有地址和密码。
迁移到 prodflow 里只记连接的名称；prod 有同名连接就能直接跑。迁移页现有的「连接预检」会提示缺哪个连接。

落地时要定的几件事

  • !现在的 HTTP 组件不能选连接：认证方式只有 None / Basic Auth / Bearer Token，直接填在步骤里。要么改 HTTP 组件，要么另做一个「带连接的 HTTP」组件；改的话，要保证现有用 HTTP 的 flow 不受影响。
  • !AP 的连接是按 workspace 存的。Admin 建一个连接，要定它给哪些 workspace 用。
  • !要先换 token、签名，或者返回 200 却可能是业务失败的接口，Basic / Bearer 连接管不了。现有的 Content Organizer 照旧保留；以后遇到这类接口再单独看。
  • !HTTP 组件底层每次请求都会关掉证书校验（fetch-http-client.ts 第 29 行）。HTTP 成了调外部系统的主路径，这个要先修。
FU 专属

把某个 FU 的业务规则写成组件

每个 Function Unit 都有只属于自己的业务规则。比如采购申请有「A 级供应商、金额满 10 万打 8 折」「申请金额不能超过部门预算」。把这些规则写进 FU 专属组件，它就变成组件面板里可以拖的一个步骤。

它有三个特点：

  • 只算：输入几个值，按规则算出结果。不查库、不调外部系统、不等人审批。
  • 数据从外面传进来：要用的数据由 flow 先调用数据 flow 取出来，再传给它；算出的结果，再由 flow 调用数据 flow 写回去。
  • 规则写在代码里，有版本：改规则就是改代码、发新版本、重新导入。改动有记录，也能写测试。

采购申请这个 FU 可能有哪些 API（每个 API 是包里的一个 action）

类型API输入输出流程里哪一步用
计算计算折扣金额、供应商等级折扣率下单前
校验检查预算申请金额、预算余额是否通过、超出多少部门审批之后
判断走向决定审批路线金额、采购类别路线 A 或 B交给流程里的网关，决定下一步找谁审批
生成生成通知内容订单号、供应商、金额邮件标题和正文审批通过后发通知

换一个 FU 也一样。比如报销申请（fu-expense）：「按职级算报销上限」输入职级和费用类型、输出上限金额；「检查发票是否重复」输入本次发票号和历史发票号（由数据 flow 查出），输出重复的发票号。

写进 FU 专属组件

  • ✓只有这个 FU 才有的规则：折扣、预算校验、审批路线判断。
  • ✓规则会改，需要留版本、写测试的。
  • ✓好几个 flow 都要用同一套规则的。

不写进去，放到别处

  • ✕读写数据库：放在数据 flow 里。
  • ✕调外部系统：用外部系统组件。
  • ✕人工审批、等待：放在流程里的 User Task。
  • ✕很多 FU 都能用的（算工作日）：做成基础工具。
  • ✕只用一次的几行小转换：用 flow 里的「代码」步骤（AP 自带，可以直接写几行 JavaScript，不能联网），不用打包。

代码长什么样（示意）

// automation/packages/pieces/community/fu-purchase/src/lib/actions/calc-discount.ts
import { Property, createAction } from '@activepieces/pieces-framework';

export const calcDiscount = createAction({
  name: 'calc_discount',        // 机器名，写进 flow，发布后不要改
  displayName: '计算折扣',
  description: '按供应商等级和金额算采购折扣',
  props: {                      // 组件面板里看到的输入框
    amount: Property.Number({ displayName: '金额', required: true }),
    level: Property.ShortText({ displayName: '供应商等级', required: true }),
  },
  run: async (ctx) => {         // 规则本身：只算，不查库
    const { amount, level } = ctx.propsValue;
    if (level === 'A') return { discount: amount >= 100_000 ? 0.08 : 0.05 };
    if (level === 'B') return { discount: 0.03 };
    if (level === 'C') return { discount: 0 };
    throw new Error(`供应商等级 ${level} 不在规则里`);
  },
});

在可点击原型里打开「采购-计算折扣」，点第 3 步，可以改金额和等级试算折扣。

FU 专属的 API 写在哪

和我们现有的自研组件放在同一个目录：automation/packages/pieces/community/。一个组件一个文件夹，FU 专属的叫 fu-<FU 名>，每个 API 是 src/lib/actions/ 下的一个文件。

类别不是目录，是按名字前缀认出来的：fu- 是 FU 专属；数据类是固定的 3 个；其余都是基础工具（包括已有的 Content Organizer）。这样不用改仓库的构建配置，community/ 本来就是放自研组件的地方。

注意两边分开放：FU 的表单、流程这些设计存在 DW 里；FU 专属组件的代码存在 Git 仓库里。两边靠命名对应（fu-purchase 对应 FU「采购申请」），再由一步 flow 的业务键把 Service Task 和组件接起来。

组件怎么开发和上线

第 1 步写代码在仓库 automation/packages/pieces/community/ 下建一个文件夹，例如 fu-purchase/
第 2 步打包打成一个 .tgz 组件包
第 3 步导入在 Admin Center「Automation Pieces」导入。dev → uat → prod 用同一个包
第 4 步使用在 DW Automation 的 flow 里，从组件面板拖出来用

flow 本身怎么上线：数据 flow 和普通 flow 都用 Admin 现有的 flow 迁移页，从 uat 导到 prod。

注意：「prod 从 Admin 导入组件」这件事（D9）还是草稿。按草稿，prod 现在只能查看和导出组件，不能导入。见第 4 件待定事项。

数据库连接

你原来说在 DW 的 flow 里配连接信息。dev 和 uat 可以这么做，但 prod 没有 DW；Admin 的 flow 迁移页也只检查目标环境缺哪些连接，本身建不了连接。所以 prod 的连接要另找地方配：

由部署环境注入
  • ✓每个环境一份，放在 K8s 配置和 Key Vault 里，和 Content Organizer 现在的做法一样。
  • ✓密码不进 flow，迁移时什么都不用带。
  • ✓「平台数据」组件运行时检查调用它的 flow 是否在数据 workspace，不在就报错。flow 作者改不了这个检查。
Admin Center 连接管理推荐
  • ✓调外部系统已经定了要做这个连接管理，数据库连接放同一处。
  • ✓prod 上也能建、改连接；连接只给数据 workspace 用，就限制住了谁能连库。
  • ✕工作量更大，还要做权限和审计。

两种都要遵守：单独开一个数据库账号，只给需要的表增删改查权限，不用 AP 自己的账号，也不用平台应用的账号。

如果连的是平台自己的 Relation Table：这些表的数据都存在一张统一的 JSON 表里，不是一张表对应一张物理表。所以「平台数据」组件要按表名找到表结构，再把条件翻译成查询；写入时还要补上 Admin 写入时会做的事：分配主键、填审计字段、记审计日志、设置状态。不补的话，flow 写进去的行在 Admin 和 Portal 里会缺东西。

如果连的是外部系统的库：现有的 postgres 组件已经能查、增、改、删，只是条件要手写 SQL。给它加一个「选字段 + 运算符 + 值」的条件编辑就行。
