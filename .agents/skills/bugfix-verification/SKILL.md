# 修复验证（Bugfix Verification）

本 skill 只解决一个问题：**「我报告已修复」和「用户实测真的好了」之间的落差。**

不是能力问题——落差几乎全部来自**把不成立的东西当成了验证证据**。
本文列出的每一条禁令都对应本仓库真实踩过的坑。

根因调查的方法（怎么修）不在本文范围；本文只管**修完之后凭什么说它好了**。

## 0. 铁律

> **没有「修复前失败 / 修复后通过」的同一条证据，就不许说「已修复」。**

只能说三种话之一：

| 说法 | 前提 |
|---|---|
| **已修复** | 拿到红→绿证据（§2），且证据不在 §3 黑名单里 |
| **已修改，未验证** | 改完了但验证手段不可用（无环境/无权限/无数据） |
| **未复现，不动** | 连 bug 都没复现出来（§1） |

**「已修改，未验证」是完全可接受的输出。** 明确允许这句话，是为了消除粉饰的动机——
含糊其辞地暗示修好了，比老实说没验证坏得多：用户会去测，白跑一趟，然后不再信任任何一次「已修复」。

## 1. 先复现 —— 复现不了就不许开始修

**动手前必须亲眼看到 bug 发生**，并留下失败证据（报错文本 / 截图 / 查库结果 / 失败测试）。

复现不了时的正确做法：

- 说明「未能复现」，列出**已经试过的具体路径**（不是"试了几种方法"）
- 问用户要复现步骤、环境、数据、账号、FU id
- **不许**凭报错文本猜一个改动交上去

> 没复现就改 = 你不知道改的是不是这个 bug，也不可能知道它好没好。
> 这种「修复」即使用户测好了也是巧合，下次照样复发。

复现时顺手记下**判据**：到底看到什么算坏、看到什么算好。这条判据就是 §2 红→绿的那把尺子，
现在不定死，改完之后会不自觉地把尺子放松到「反正没报错」。

## 2. 红 → 绿：必须是同一条证据

```
修复前跑 X → 失败（记录输出）
修复后跑 X → 通过（记录输出）
```

**X 必须是同一件事**。常见的偷换：修复前看的是 UI 报错，修复后看的是单测通过——
这是两条不同的证据，证明不了任何事。

优先级从高到低：

| 手段 | 何时用 |
|---|---|
| **先写失败测试**，再修到绿 | 逻辑类 bug 的首选。测试本身就是红→绿证据 |
| 真实 UI 操作 + 截图 | 可见行为类。修复前后各一张 |
| 查数据库确认业务状态变了 | 涉及保存/流转/权限。**不能只看接口返回 200** |
| 命令输出对比 | 构建/脚本类 |

### 新写的回归测试必须先证明它会红

补测试时**先把修复临时关掉**（`if (false && ...)` / 删掉新传的参数 / 还原那一行），
确认测试真的 FAIL，再恢复。

没做这一步的回归测试经常是**恒绿的摆设**——尤其在 bugfix 场景，很容易写出一个
「无论修没修都成立」的断言，然后它会一直绿到下次复发。

## 3. 假证据黑名单

以下**全部不构成**「已修复」的证据。每一条都是本仓库真实踩过的：

| 假证据 | 为什么不算 | 正确做法 |
|---|---|---|
| 编译通过 / IDE 无红线 / 「理论上能跑」 | 类型对 ≠ 逻辑对 | 跑真实路径 |
| **单测全绿** | 实测：1594 全绿仍漏 Blocker（`as any` 让 TS 放行、该路径无覆盖） | 截图 + 查库 |
| **exit code = 0** | 后台任务通知的 exit code 反映管道最后一环（`tail`）**不是 `mvn`** | Read output 看 `BUILD SUCCESS` / `Tests run` |
| `mvn test` 后直接测镜像 | Dockerfile 只 COPY `target/` 里的 jar，`test` 不打包 → **镜像里是旧 jar** | 先 `mvn package` 再 build |
| 改完直接刷页面 | 后端有 5min 缓存 / Hibernate 缓存实体元数据 | **重启对应服务**再测 |
| 新增 init-script 后直接测 | init-scripts 只在数据卷为空时执行，对老库**永不生效** | 手工 psql 执行 + 重启后端 |
| 只看 HTTP 状态码 | 静默失败照样 200 | `curl` 看 **body** |
| 只看 toast 消失 / 报错没了 | 静默失败没有报错 | 查库确认业务状态**真的推进了** |
| diff 产物说 IDENTICAL | 血泪：`sed` 抹掉 `data-v` 正好抹掉唯一差异 | CSS 终审必须是**运行时 computed style + 截图** |
| 只在一个 FU / 一份 seed 数据上过 | 硬编码和名字猜测只在部分 FU 复现 | **双样本**：新建 FU + 已有/导入 FU |
| 只用自己的账号存一次 | 隔离/归属类 bug 的受害者是**别人**那份数据 | 换主体保存，查库确认对方数据没变 |
| 只验一类入口 | 同一函数被多类页面调用，走的分支不同 | grep 出所有入口类型，每类各验一次 |
| 专项门禁绿（如 `regression:mi`） | 门禁只覆盖热路径 | 跑全量，并先记基线区分「既有红」 |

## 4. 改动前先记基线

跑全量测试**之前先 `git stash` 记一次基线**，否则分不清「既有红」和「我弄红的」。

本仓库多处遗留红基线（见记忆 / 各阶段进度文档）。不记基线就会出现两种错误：
把既有红当成自己的回归（白改半天），或把自己的回归当成既有红（**发出去**）。

## 5. 报告格式

报告「已修复」时必须写全这四项，缺一项就降级成「已修改，未验证」：

```markdown
## 修复验证

- **复现**：<怎么复现的 / 修复前看到什么>
- **根因**：<一句话>
- **红→绿证据**：
  - 命令/操作：...
  - 修复前：<失败输出>
  - 修复后：<通过输出>
- **未验证项**：<哪些没验 + 为什么>  ← 没有就写「无」，不许省略
```

**「未验证项」是必填**。省略它等于隐性宣称全都验过了。

## 6. 自检清单

- [ ] **修之前**亲眼复现了 bug，留下失败证据
- [ ] 复现时定死了判据（看到什么算好），改完没有放松这把尺子
- [ ] 红→绿是**同一条证据**，不是修复前看 A、修复后看 B
- [ ] 新写的回归测试**临时关掉修复验证过它会红**
- [ ] 证据不在 §3 黑名单里（逐条对过，尤其：单测绿 / exit code / 没重启 / 只看状态码）
- [ ] 涉及镜像 → 先 `mvn package` 再 build；涉及后端改动 → **重启服务**
- [ ] 涉及 UI → 修复前后各一张截图 + 控制台 0 错误
- [ ] 涉及保存/流转/权限 → **查库**确认业务状态真的变了
- [ ] 涉及 FU 语义 → **双样本**（新建 FU + 已有/导入 FU）
- [ ] 涉及隔离/归属 → 换第二个主体验过「不影响别人」
- [ ] 跑全量前**记了基线**
- [ ] 报告写全四项，**「未验证项」没有省略**

## 7. 与其他 skill 的关系

| 场景 | 用什么 |
